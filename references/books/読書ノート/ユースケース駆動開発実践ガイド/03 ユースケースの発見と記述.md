# 第3章 ユースケースの発見と記述

ユースケースは、利用者が何を求め、システムとの対話を通じてそれをどう達成するかを記述する。その対話を具体的にたどると、ソフトウェアが行う仕事と、途中で起こり得る別の事態が見える。第3章の中心は、この記述をドメインモデルの言葉で明確にし、設計・見積もり・テストへ渡せるようにすることにある。図を描いたり、テンプレートの空欄を埋めたりするだけでは、その仕事は明らかにならない。（3.1〜3.2）

以下の記述例は、原文を逐語的に転載したものではない。書籍が実際に示す各版について、変更箇所とその理由を追えるように整理した要約である。書店の画面、条件、役割は書籍の例の設定として読む。

## 要求の一覧から、設計できる対話へ進む

機能要求の一覧には、大きな目的と細かな条件が順不同に混在しやすい。そのままでは、実現に必要な仕事や規模を判断しにくい。著者は、顧客との会話や画面の紙芝居も情報源にしながら、ユースケースと予備設計によって不確実な部分を明らかにする。書く際には「何が起こるか」で場面を始め、「次に何が起こるか」で通常の流れを進め、「ほかに何が起こるか」で分岐を探す。（3.1、3.2の指針10）

通常の流れが基本コースであり、エラーや通常とは異なる使い方の流れが代替コースである。基本コースだけを詳しくしても、入力不備や失敗に対応する機能は見えてこない。著者は、利用の多くが基本コースを通る一方、必要な機能の多くは代替コースから現れる、と「90%」を使って強調している。ここでは測定済みの一般的な比率としてではなく、代替コースの検討を省かないための説明として受け取る。（3.1）

この作業を支える言葉が、第2章で作った初期ドメインモデルである。最初から完全なモデルを待つ必要はなく、ユースケースを書いて不足を見つけたらモデルへ戻す。その後もロバストネス分析とシーケンス図によってモデルを更新し、静的な構造と動的な振る舞いを対応させていく。具体的な対話は、その後の設計とテストの出発点にもなる。（3.1、3.2の指針5〜4）

## ログインの例：能力の表明から、実際の対話へ直す

最初の記述は、パスワードを使ってログインできる、という能力を述べている。

```text
記述1
利用者は、パスワードで認証してログインできる。
```

この一文では、誰が何を入力し、システムが何を確かめるのかが分からない。何が可能であるべきかを述べる機能要求にとどまり、そのための対話は示されていない。そこで、利用者とシステムの行動を順に書き出す。（3.2の指針8）

```text
記述2
利用者がユーザー名とパスワードを入力し、ログインをクリックする。
システムがユーザー名で情報を取り出し、パスワードを照合する。
利用者がシステムへログインする。
```

修正によって、入力・取得・照合という仕事が現れた。しかし、対話の始まりを利用者の入力に置くと、入力画面を表示するための仕事が省かれることがある。次の指針では、その前にシステムの応答を補う。（3.2の指針7、図3.2）

```text
記述3
システムがログイン画面を表示する。
利用者がユーザー名とパスワードを入力し、ログインをクリックする。
システムがユーザー名で情報を取り出し、パスワードを照合する。
利用者がシステムへログインする。
```

画面に既存データを出す場合には、その表示の前に取得や初期化も必要になる。システム側から書き始める例は、この仕事を見落とさないために示されている。常にシステムから始めるという規則ではなく、利用者側から始まる対話もある。どちらの場合も、利用者の行動だけで終わらず、システムがどう応じるかを書く。なお、この例は基本コースであり、ユーザー名やパスワードが見つからない場合の流れも必要だと章末注が補っている。（指針7、章末注2）

書籍は、要求として可否や義務を述べる書き方を「指示的」、実際に何をするかを述べる書き方を「叙述的」と呼んでいる。訳注1では、原語の passive voice／active voice をそのまま文法上の受動態・能動態として扱わず、この意味に置き換えたと説明する。したがって、直す対象は単なる語尾ではない。記述1に隠れていた行動と応答を、記述2・3のように読み取れる形にすることが要点である。

## 購入予定リストの例：同じ概念を同じ名前で呼ぶ

対話の順序が書けても、そこで使う言葉がモデルと一致していなければ、設計対象を特定できない。次の例では、同じものを別名で呼ぶ問題と、画面名が不明確な問題を二段階で直している。（3.2の指針2〜1）

| 段階 | 記述の要約 | 残っている問題／変更の意味 |
| --- | --- | --- |
| 記述1 | 利用者がタイトルを選び、「後日買う予定の書籍一覧」へ加える。システムが更新された一覧と「ユーザーカート」のタイトルをページに表示する。 | タイトル・書籍、書籍一覧・購入予定リスト、ユーザーカート・ショッピングカートが混在する。どの概念を指すかを読み手が推測しなければならない。 |
| 記述2 | 利用者が書籍を選んで購入予定リストへ加える。システムが更新された購入予定リストと利用者のショッピングカートをページに表示する。 | ドメインモデルの名称へ統一した。たとえば「後日買う予定の書籍一覧」を、別の書籍一覧ではなく購入予定リストとして特定できる。ただし、どのページに表示するかはまだ不明確。 |
| 記述3 | 同じ操作の後、システムが購入予定リストページを表示する。その画面に更新された購入予定リストとショッピングカートが示される。 | バウンダリとなる画面にも名前が付いた。表示先と、そこで必要になる情報を具体的に検討できる。 |

画面名の明確化が必要なのは、見た目を細かく指定するためだけではない。著者は別の例として、精算ページなら既定の支払い方法や配送先住所を表示するための初期化が必要になると説明する。「ページ」とだけ書いた場合には、その仕事を見落としやすい。

このように、ドメインクラス名とバウンダリの名前を使うと、文章中の名詞をオブジェクトのインスタンスへ、動詞をそれらの間のメッセージや論理的な処理へ対応させやすくなる。指針3の「名詞―名詞―動詞」は、後でシーケンス図へ進むための準備である。この段階で、動詞ごとに実装クラスを作るよう指示しているわけではない。（指針4〜1）

## 画面を使って対話を確かめ、内部の計算とは分ける

画面の紙芝居は、利用者が何を操作し、その結果何を見るのかを確かめる助けになる。カート編集の例では、書籍一覧の表示、数量の変更、更新操作、変更後の数量と合計の表示を画面と対話で対応させる。ボタンやメニューを眺めれば、文章にない操作も探しやすい。（3.2の指針6、図3.3）

一方、見栄えのよい試作品ができると、代替コースの分析を終える前に、そのまま完成品へ育てる圧力が生じる。著者はその対策として、ラフな紙芝居にする、単純な線画で対話へ注意を向ける、CASEツールから関連画面を参照できるようにする、という方法を示す。図3.4のツール画面は、その紐付けの具体例である。部品を数ピクセル動かす議論や、その時点のUI実装方式が対話の検討を置き換えないことが重要になる。

対話を詳しく書くことは、すべての内部処理を展開することとも異なる。たとえば推薦書籍一覧の生成や一覧のソートは、内部では複雑なアルゴリズムでも、利用者とシステムの対話から見れば一つのステップである。ユースケースには処理の名前を書き、詳細を別の場所で記述して参照する。表3.2は、イベントと応答を扱うユースケースと、内部の計算手順を扱うアルゴリズムを比較している。（3.2「ユースケースかアルゴリズムか」）

## レビュー投稿の例：詳しくしてから、範囲と分岐を整える

書店の「読者レビューを書く」は、一つの記述を繰り返し直す例になっている。最初は、利用者が商品についてレビューを入力し、評価を決め、レビューがモデレータへ送られる、という短い筋書きだった。利用者とシステムのやり取りを含んではいるが、実際に何をするかを設計するには説明が足りない。（3.2「ユースケースの洗練」）

**第1修正版では、操作と応答を補う。** 顧客が書籍を選ぶと詳細ページが表示され、レビューを書く操作で記入画面へ進む。顧客は本文と五段階評価を入力して送信する。システムは本文の長さと評価範囲を確かめ、確認画面を表示し、追加前の確認を担うモデレータへレビューを送る。これによって、画面、検証、外部の役割が見えるようになる。

**第2修正版では、開始点を直す。** 書籍を選んで詳細を見る部分は、別のユースケースにも属する。これを毎回取り込むと記述が重複するため、現在表示中の書籍についてレビューを書く操作から始める。残りの入力・検証・確認・送付の流れは保つ。単に文章を短くする修正ではなく、このユースケースが扱う範囲を明確にする修正である。

**さらに、モデルと名前を照合する。** 記述からは書籍レビューと書籍評価に加え、新たなアクターであるモデレータ、レビュー記入ページが見つかる。また、モデルで利用者を「顧客」と呼ぶため、ユースケースの名前も「読者レビューを書く」から「顧客レビューを書く」へ合わせる。評価の検証を明記したことは、後のロバストネス分析で処理を見つける手掛かりになる。

ここまでで整ったのは基本コースである。そこには、ログイン済みで、長さも評価も正しく入力されるという暗黙の条件がある。著者は「ほかに何が起こるか」を繰り返し、未ログイン、長すぎる本文、短すぎる本文を順に見つける。クライアント側の入力検証があっても、正しい値しか届かないと決め付けず、条件が崩れた場合を考えている。（3.2「基本コースと代替コース」）

| 見つかった事態 | 書籍が追加した代替コースの要約 |
| --- | --- |
| 利用者が未ログイン | ログインを経て、レビュー記入画面へ進む。 |
| 本文が1 MBを超える | レビューを拒否し、拒否した理由を示すメッセージを表示する。 |
| 本文が10字未満 | レビューを拒否する。この例では、その後の詳しい応答は示されていない。 |

これらの数値は書籍の例の条件であり、他の製品へそのまま適用する基準ではない。また、この三つで検討を終えるとも述べていない。各行を読みながら、どこで違うことが起きるか、利用者が別の行動を取らないかを問い続けるのが次の作業になる。

## アクターと図で全体を整理し、関係の意味を本文へ戻す

一つずつ対話を書くと同時に、誰のどの利用場面を扱っているかを全体の中に位置付ける必要がある。アクターはシステムの外側にある役割で、人間だけでなく外部システムも含む。同じ人が複数の役割を担うことも、一つのユースケースに複数の役割が関わることもある。したがって、図のアクターをそのまま個人の一覧と考えない。ユースケース図は、そうした役割と利用場面の関係を概観するために使う。（3.2の指針9、図3.1）

書店では、ユースケースを一般、管理、買い物、検索の四つのパッケージへ整理している。一般にはログインや注文履歴、買い物には精算やカート編集、管理には在庫や発送、検索には著者・タイトルなどからの検索が置かれる。パッケージは階層化でき、担当する仕事の範囲を捉える助けにもなる。図3.5〜3.9はこの整理を示すが、すべての関連線を描き切ることを優先してはいない。各ユースケースの本文を明らかにする仕事が先にある。（3.2、図3.5〜3.9）

複数のユースケースに共通の振る舞いがある場合は、同じ説明を繰り返す代わりに呼出しとして分けられる。ただし、図に矢印を加えるだけでは対話は定まらない。精算から発送を呼ぶなら、どの操作・応答に続いて発送のユースケースへ移るかを、精算の本文にも書く必要がある。

| 書籍で比較する関係 | 読み取る意味と注意 |
| --- | --- |
| 汎化 | 子が親の一種であり、振る舞いを継承・変更する。図3.9では各検索が書籍検索の種類として示される。 |
| includes | AがBを包含する場合、Aの中でBの処理を呼び出す。表3.1では関数呼出しに似たものとして説明する。 |
| extends | AがBを拡張する場合、特定の条件・拡張ポイントで、Bの流れへAの振る舞いが加わる。矢印は拡張側Aから元のBへ向かうため、呼出しの流れと同じ向きには読めない。 |
| invokes | 著者が使う呼出しの表記。AからBを実行することを、呼び出す側から呼ばれる側へ表す。 |
| precedes | AがBに先行する場合、Bが始まる前にAを完了している必要がある。ログインと精算の例で使われ、実行中の呼出しとは異なる。 |

著者が invokes と precedes を好む理由は、非技術者も含めた読み合わせで、呼出しと先行の意味を理解しやすいからである。通常のオブジェクト指向分析・設計では、関係表記を選ぶ議論より、ユースケース中の実際のステップを明らかにすることを重視する。また、クラスの汎化によるコード重複の除去と、ユースケース記述の整理は同じ効果ではないとして、後者で汎化を使い過ぎることにも疑問を示す。（表3.1、共通の振る舞い・ステレオタイプに関するコラム、訳注2）

ただし、includes と extends の違いが常に不要だと一般化はできない。書籍自身が、コードをユースケース単位に構成するアスペクト指向の場合を例外として挙げている。アスペクトのコラムでは、セキュリティやトランザクション管理など、複数のクラスへまたがる関心事を取り上げ、独立したピアユースケースと、それを補う拡張ユースケースを区別する。元のコードを直接変更せず、ポイントカットやアドバイスで拡張する構成では、この違いが設計上の意味を持つ。これは本章の推奨に付いた適用範囲の説明である。

## テンプレートの長さより、対話を検討できているかを見る

指針10の「二段落ルール」は、基本コースと代替コースへ注意を集中させるために示される。長すぎるユースケースは、それに対応するシーケンス図も理解しにくくなる。また、長い記述の中に、対話ではなく機能要求を混ぜてしまう場合もある。長さは、責任のまとまりや記述の種類を見直すきっかけになる。（3.2の指針10）

後半では、コーバーンの完全形式のテンプレートを掲げ、コンテキスト、スコープ、レベル、主アクター、利害関係者、事前条件、保証、トリガー、主成功シナリオ、拡張などの項目を比較する。著者は、理論的に網羅的でも、実際のチームでは記入に時間を費やし、モデリング全体を遅らせ、基本・代替コースの検討よりフォームを埋めることへ意識が向く危険を挙げる。（3.2「ユースケーステンプレートに関する2つの考え」）

著者は長いテンプレートの利用に強く反対し、基本コースと代替コースからなる簡潔な形式を推奨する。同時に、この批判をモデリングそのものをやめる理由にしないよう補足している。章末の自習問題では、長いテンプレートが分析麻痺を招くという主張を読者自身が反論または擁護するよう求める。著者の推奨を理解したうえで、その理由を検討し直す課題である。

## 演習：どの情報を明確にし、どの重複を外すか

3.3の三つの演習では、曖昧さを減らす修正と、過剰な詳細を整理する修正の両方が示される。

**演習3.1「著者で検索する」では、画面を特定する。** 元の記述は、検索フォームを持つページを表示し、著者名を入力して検索し、書籍を一覧表示するという流れだった。該当なしの場合も、結果がないと知らせるページ、としか書いていない。解答は、検索ページ、検索結果ページ、該当なしを示すページに明確な名前を付ける。操作を増やすのではなく、どのバウンダリを指しているかを明らかにする修正である。

**演習3.2「ショッピングカートを編集する」では、三つの問題を分けて直す。** 元の記述は、ログイン済みでカート編集ページを表示中という事前条件を置き、利用者が商品を追加・削除して更新する、とまとめていた。代替コースは、カートが空なら商品を削除しない、というものだった。

| 問題と理由 | 解答での修正 |
| --- | --- |
| 表示済みという事前条件が、初期表示に失敗する場合を隠す。そのままではロバストネス図、設計、見積もり、テストにもその経路が現れない。 | カートページを表示するところから本文を始める。 |
| 基本コースが一つの具体的な場面ではなく、複数の選択肢を曖昧にまとめている。このページでは新しい商品の追加はせず、削除か数量変更を行う。 | まず取扱品の削除を操作し、システムが削除後のカートを表示する。続いて数量を1から2へ変えて更新すると、システムがカートを更新し、合計を再計算して再表示する、と順を追って書く。 |
| 代替コースが本文のステップと結び付いておらず、起こり得る別の事態も欠けている。 | 古い画面から選んだ商品がすでに存在しない場合、数量0の場合、負数や数字以外の場合を加える。 |

追加された代替コースでは、二つのウインドウの片方が古い場合を例に、操作失敗を知らせてカートを再表示する。数量0は削除として扱い、負数や数字以外なら元の数量を保った画面と不正入力のメッセージを示す。ここで学ぶ点は、事前条件という欄の一律禁止ではなく、書いた条件が必要な処理や失敗を検討の外へ追い出していないか、という具体的な確認である。

**演習3.3「アカウントを作成する」では、詳細を適切な場所へ移す。** 元の基本コースは、ユーザー名、パスワード、その確認、氏名、住所、郵便番号、電話番号、メールアドレスなどをすべて列挙していた。解答では、これらを顧客アカウントの属性として定義し、ユースケースからその定義を参照する。入力、登録操作、ユーザー名の重複確認、アカウント作成、完了の表示という流れは残す。パスワード不一致と名前重複の代替コースも残り、必要な入力情報を失わずに重複を減らしている。

検索の例では名前を補い、カートの例では具体的な応答と分岐を増やし、アカウントの例では情報の置き場所を変えた。これらの修正を合わせて読むと、詳しければよい、短ければよい、という判断では足りないことが分かる。設計する対話が明確で、必要な情報の定義へたどれるかが判断の軸になる。
