# 第6章 予備設計レビュー

予備設計レビューは、ユースケースの文章、ロバストネス図、更新したドメインモデルを照合し、詳細設計へ進めるかを確かめる節目である。図ができていても、入力の格納先へ届く処理や、別のユースケースへ仕事を引き渡す方法が抜けていることがある。本章は「顧客レビューを書く」の文章と図を順に直し、何が不足していたか、修正すると何が新しく分かったかを示す。

## 要求レビューを終えた後にも、三つの成果物を照合する

第4章の要求レビューでは、要求、ユースケース、ドメインモデルの対応を確かめた。その後のロバストネス分析では、文章を図へ移す過程で、画面やデータ、必要な働きが見つかり、文章とモデルが更新される。したがって、以前にレビューを通っていることは、更新後の成果物が互いに一致していることを保証しない。ユースケースのまとまりごとに、改めて文章・図・モデルを読み合わせる必要がある。（章導入、6.1のQ&A）

このレビューは、必要なエンティティの属性、画面の名前、画面とデータの間の流れを、詳細設計前に確認する機会でもある。たとえば画面で入力を受け取ると書いたなら、その値をどこへ保持するかをモデルで確かめる。画面に情報を表示すると書いたなら、その情報を得られる対象や属性があるかを逆向きにたどる。こうして、後の設計者が想像で補わなければならない箇所を減らす。（6.1のQ&A、指針9・8）

著者は、顧客の代表、開発者、主要な管理者など、要求レビューに参加した人を予備設計レビューにも招く。そのうえで、この節目を顧客が設計へ直接関与する最後の機会とし、以後の詳細設計は主に経験のある開発者が扱うという進め方を述べる。これは、顧客が新しい要求や画面への意見を述べることまで禁じる説明ではない。新しい要求が生じれば、最初の段階へ戻ってユースケースとドメインモデルを変更する。著者が強く避けようとしているのは、技術的な設計やコーディングを非技術者・半ば技術に詳しい顧客が指揮することである。この参加方針は著者の立場として読み、一般に必須の運営規則とは扱わない。（6.1のQ&Aと補足）

テクニカルアーキテクチャも、この時点で検討・レビューする必要がある。詳細設計は、採用する技術的な構成を前提に進むからである。ただし、ユースケースに設計パターンやクラス生成の仕組みまで書き込むこととは別であり、アーキテクチャそのものの説明は第7章へ続く。（6.1のQ&A、6.3）

## 蛍光ペンで、文章と図を両側からたどる

十の指針の中心にあるのは、文章と図の対応を目で確認する方法である。基本コースの一段落を読み、対応する図の要素を蛍光ペンで塗る。代替コースにも同じことを行い、本文をすべてたどったら、図全体を見て、塗られずに残った図の要素がないかを調べる。文章だけにある動作と、図だけにある処理のどちらも修正対象になる。著者が安価な蛍光ペンでできるテストとして紹介するのは、道具の高度さより、両者を具体的に照合することに価値があるためである。（6.1指針10）

基本コースとすべての代替コースを同じ図で確認できれば、途中の分岐や復帰も追いやすい。基本コースと代替コースを色分けする方法も挙げられるが、色分け自体が目的ではない。図が大きくなりすぎたり、代替コースにさらに代替コースが必要になったりするなら、ユースケースの分割を検討する。一つの図へ押し込むことを優先しない。（指針10、6.2末尾）

図で発見したエンティティは、ドメインモデルにも戻す。図だけに新しい対象を置いたままでは、静的なモデルとの対応が失われる。著者は忘れを防ぐ作業順として、先にクラス図へ新しい対象を追加し、エンティティとして設定してからロバストネス図へ持ってくる方法を勧める。重要なのはそのツール操作自体ではなく、図の中で必要になった対象や属性を、共通のモデルにも反映することである。（指針9）

## 分岐名だけでは、代替コースを確認できない

代替コースのレビューでは、「エラーが起きる場合」を挙げただけで終えない。その条件が起きたときに、利用者が何をし、システムがどう応じるかまで、基本コースと同じように確かめる。代替コースにはエラーだけでなく、頻度が低い操作や、通常とは違うが許されている使い方も含まれる。条件名の一覧では、それらを処理する仕事が図にも設計にも現れない。（6.1指針7）

著者は、多くの複雑さが代替コース側にあり、そこを省くと必要なクラスや操作も大量に抜けると警告する。この指摘は、失敗条件を増やせというだけの話ではない。失敗後の説明、別の選択、再試行や復帰など、そこで必要な対話を記述して設計へ渡す、という要求である。（指針7）

同じ理由で、利用者の操作だけを書いたユースケースも不十分になる。画面を開く、入力する、送信するという操作を並べても、システムが何を確認し、何を保存し、何を返すかは決まらない。ユースケースは双方の対話として読み、特にシステム側の仕事が抜けていないかを調べる。（指針6）

## 接続規則と用語で、隠れた処理を見つける

ロバストネス図の接続規則は、図の形式だけを取り締まるためのものではない。アクターはバウンダリとつながり、バウンダリ同士、バウンダリとエンティティ、エンティティ同士は直接つながない。名詞で表す二つの対象の間には、動詞で表す働きが必要になる。画面とデータを線で結んだだけの箇所を見つけたら、そこで行われるはずの処理を問い直せる。（6.1指針5）

著者は、ロバストネス図を適切に描けないまま、より難しいシーケンス図へ進むことを戒める。問題は図を描く作業の苦手さだけではなく、要求や対象を十分に理解していない可能性にある。ツールによる規則チェックも役立つが、図の接続が通ることだけでは必要な振る舞いを保証できない。拾い出したコントローラは、後の単体テストを考える手掛かりにもなる。（指針5と補足）

文章の語彙も、この照合を助ける。画面には明確な名前を付け、扱う対象にはドメインモデルと同じ名前を使う。曖昧な業務説明のままでも、技術者だけに分かる実装用語だらけでも、顧客と開発者が同じ内容を確認できない。著者はユースケースを両者の小さな契約にたとえ、どちらにも意味が分かる具体度を求める。（指針4・3）

ここで明確にするのは、必要な対象と振る舞いである。その仕事をどのクラスのメソッドへ割り当てるかは、次の詳細設計で決める。著者は二段階に分け、まずオブジェクトや画面を見つけて文章を明確にし、その後に責務を割り当てる。実装クラスの配置や設計パターンの当てはめに気を取られると、要求の不足を探す作業が埋もれてしまう。（指針3・2）

第2章は、パターンの検討を通常はロバストネス分析の段階から始めると説明していた。本章の確認は、その当てはめを目的化せず、ユースケースの振る舞いと必要な対象を明らかにすることに焦点を保つ、というものになる。技術的な前提を検討することと、ユースケース本文へ実装詳細を書き込み、責務の割り当てを終えたことにすることを区別する。第7章の掲載順と実際の技術検討の時期については [[読書ノート/ユースケース駆動開発実践ガイド/07以降の補足調査]] に整理した。

この考え方を、最後の指針では次の六つの確認へまとめている。（指針1）

1. ユースケース記述とロバストネス図が一致しているか。
2. 図が接続規則を守っているか。
3. 処理の流れが論理的につながっているか。
4. 必要な代替コースを扱っているか。
5. 設計パターンの適用に気を取られていないか。
6. 詳細設計を先取りしていないか。

## 「顧客レビューを書く」：図と文章を順に直す

6.2では、第5章から引き継いだ図を、分析者とレビューアの対話で見直す。以下は変更点を追うための要約であり、書籍のユースケース記述の転載ではない。書店の例で見つかった対象や属性を、別のプロジェクトでも必要な概念として採用するものでもない。

### 1．入力された値が、レビューの格納先に届いていない

最初の図には、顧客、レビュー入力ページ、顧客レビューというエンティティがある。しかし、入力ページと顧客レビューがつながっていない。顧客が送信を押すところは表れていても、入力した本文と評価をどのように格納するかが欠けている。（図6.1）

分析者は、入力ページから顧客レビューへ一本の線を引けばよいと考える。レビューアは、バウンダリとエンティティを直接結ぶと接続規則に反すると指摘する。二つの名詞の間に必要な動詞を考え直すことで、本文を記入する働きと、評価を入力する働きが見つかる。（図6.1→6.2）

```text
図1：入力ページと顧客レビューが別々に置かれている。
途中の案：入力ページ ─ 顧客レビュー、と直接結ぶ。
問題：値を受け渡す働きを書かず、名詞同士の線で済ませている。
図2：入力ページ → 本文を記入する働き → 顧客レビュー。
                    評価を入力する働き → 顧客レビュー。
```

ここで、Webフォームならブラウザが入力値を送信するので、処理を描く必要がないのではないか、という疑問が扱われる。著者の回答は、これは実装コードの構成図ではなく、ユースケースに書かれた仕事を確認する図だというものだ。実装環境が一部を担うとしても、入力値を扱う仕事そのものが要求から消えるわけではない。（6.2の補足）

章末注4は、この区別を実装例で補足する。一般的なGUIアプリケーションでは、入力欄からフォーカスが外れるなどのイベントに応じて値を取り出す処理が必要になる。一方、本書が想定するWebフォームでは、ブラウザが送信時にフィールドの値をサーバへ渡す。図6.2のコントローラを、そのまま独立したイベント処理や実装クラスとして作れという意味ではない。

### 2．送信ボタンを押すと、どの処理が動くのか

二つの入力処理を加えても、まだ問題が残る。入力ページから複数のコントローラが出ているのに、送信というラベルは顧客から入力ページへの線に付いている。これでは、顧客がそのページで送信することは分かっても、ページから先のどの働きへ進むかが分からない。（図6.3）

レビューアは、利用者の操作を示すラベルを、バウンダリから該当するコントローラへ出る線へ付けるよう促す。図6.4では、送信から表示処理、確認ページへと対応を追えるようになる。変更は線の見た目を整えるためではなく、複数の操作と処理の対応を区別するためである。（図6.3→6.4）

```text
図3：顧客 ─「送信」→ 入力ページ → 複数の処理。
問題：ページの先で、送信に対応する処理を特定できない。
図4：入力ページ ─「送信」→ 対応する表示処理 → 確認ページ。
```

### 3．二つの「表示する」は、何を表示するのか

次にレビューアは、二つの検証失敗が同じ拒否ページへ進む部分を調べる。一つはレビュー本文の長さ、もう一つは評価の範囲の確認であり、それぞれの失敗経路に「表示する」というコントローラがある。分析者は、別々の表示処理として置くことには意味があると説明する。レビューアもその区別を認めるが、同じ名前では、利用者に何を伝えるのかが分からないと指摘する。（図6.5）

修正では、表示する理由をコントローラ名へ入れる。図6.6では、長さの最大値を超えたことを知らせる処理と、評価が範囲外であることを知らせる処理が区別される。条件に引っ掛かったという内部の判断から、利用者へ返す具体的な説明までを表す変更である。（図6.5→6.6）

```text
図5：長さの確認に失敗 → 表示する → 拒否ページ。
     評価の確認に失敗 → 表示する → 拒否ページ。
問題：別の拒否理由が、同じ抽象的な処理名に隠れている。
図6：長さの上限超過を知らせる処理 → 拒否ページ。
     評価の範囲外を知らせる処理   → 拒否ページ。
```

なお、対話では短すぎる入力の例も挙げられるが、図6.6の長さに関するラベルは最大長の超過を示す。この例の主眼は拒否理由を具体化することであり、その一つのラベルですべての長さ違反が説明できていると読み替えない。

### 4．「審査へ送る」だけでは、次のユースケースへつながらない

最後の見直しは、図だけでなく文章へ戻る。初めの記述は、確認ページを表示し、レビューをモデレータへ送るという内容だった。モデレータの作業を別の「顧客レビューを審査する」で扱うことには合意している。しかし、投稿する側から審査する側へ、レビューがどのように渡るかは記述もモデリングもされていない。（6.2「ユースケース記述から詳細が漏れている」）

分析者は、審査のためのキューへレビューを格納し、そのキューを審査ユースケースが処理する、と書き直す。これで受け渡しの仕組みは一歩具体的になるが、レビューアは、単にキューと書くだけでは対象との結び付きが不足すると指摘する。送信済みレビューを追跡するための対象をモデルに加え、名前を与える必要がある。

```text
記述1：確認ページを表示し、レビューを審査担当へ送る。
問題：別のユースケースへ、何を介して引き渡すのか不明。

記述2：確認ページを表示し、審査のためのキューへレビューを格納する。
       審査ユースケースが、そのキューを処理する。
問題：格納先の対象がモデルに存在せず、名前も定まっていない。

記述3：確認ページを表示し、顧客レビューを待機レビューキューへ追加する。
       そのキューを「顧客レビューを審査する」が処理する。
```

ここで「待機レビューキュー」という対象が発見される。さらにレビューアは、どの本に対するレビューかを保持するため、顧客レビューに書籍IDの属性が必要だと指摘する。キューのクラスと合わせてモデルへ加えることで、文章の具体化が、新しい対象と属性の発見へつながる。キューという語があるから特定のメッセージ基盤を採用する、といった技術選択まで決まったわけではない。（6.2、図6.7）

## 完成図は、文章と対象を結び付けた結果として読む

図6.7には、ログインの確認、レビュー本文と評価の入力、検証と拒否理由の表示、確認ページ、書籍との結び付き、待機レビューキューへの追加、審査ユースケースへの引き継ぎがまとめられている。本文を読みながら図をたどれる形になったのは、最初からこの図を正解として置いたからではない。入力値の行き先、操作と処理の対応、失敗時に返す説明、次のユースケースへの受け渡しを順に問い、文章とモデルを直した結果である。

著者は、図をたどる配置の目安として左上から右下を挙げるが、絶対的な規則とはしていない。また、この完成例自体がかなり大きく、ユースケース記述も第3章の二段落という目安に近いと述べる。さらに複雑になるなら、複数の小さなユースケースと図へ分けることを真剣に検討する。完成例の大きさを、どのユースケースでも目指す標準にはしない。（6.2末尾）

予備設計レビューを通った状態とは、文章と図が相互に一致し、期待するシステムの振る舞いを表し、必要な対象と属性がモデルにそろった状態である。この確認を終えてから、テクニカルアーキテクチャを踏まえ、シーケンス図で仕事の割り当てを考える。図6.8は、ロバストネス分析による文章の明確化とモデルの更新が、予備設計レビューへ集まる位置関係を示している。（6.3、[[Highlight and Note/Books/ユースケース駆動開発実践ガイド#^kb-b01b5mx2tc-3899-12d319b5|位置3899の既存ハイライトとメモ]]）

章末には四つの注がある。最初の三つは、別文献への参照、技術者だけに通じる言葉の補足、六つのレビュー手順を詳述するワークブックへの案内である。四つ目は前述のGUIとWebフォームの入力処理の違いを説明する。本章に独立した練習問題・解答の節はなく、分析者とレビューアの対話が、指針を実際に適用する例になっている。
