## Policy Cloud への接続

現行の入口は [.claude/commands/define-spec.md](</Users/tatsumi.watanabe/projects/policy-cloud/main/.claude/commands/define-spec.md:23>) と [pm-agent.md](</Users/tatsumi.watanabe/projects/policy-cloud/main/.claude/agents/pm-agent.md:46>)。問題・背景 → ユーザーストーリーと受け入れ条件 → 影響調査 → Issue 草案という流れを、上記のモデルとユースケースで補う。

[既存 Issue テンプレート](</Users/tatsumi.watanabe/projects/policy-cloud/main/.claude/skills/requirements-definition/references/issue-templates.md:3>) には次のように渡す。

- 問題と望む成果 → 背景・課題。
- アクターの達成目標と価値 → ユーザーストーリー。
- 成功結果と重要な代替・例外の、観測できる振る舞い → 受け入れ条件。
- 対象境界と未採用の候補 → 対象外。
- モデル、影響範囲、依存関係、未決事項 → 技術的メモと参照先の設計文書。

受け入れ条件の件数を共通 skill の品質基準にしない。プロジェクトに渡す時点で現行テンプレートに合わせる。業務モデルと実装の調査は区別し、既存テーブルを業務概念の正解とはみなさない。

用語は [ubiquitous-language](</Users/tatsumi.watanabe/projects/policy-cloud/main/.claude/skills/ubiquitous-language/SKILL.md:12>) を参照するが、設計文書と食い違う場合は差を残して確認する。例えば [顧客企業と政策関係組織](</Users/tatsumi.watanabe/projects/policy-cloud/main/docs/design/PERSON_ORGANIZATION_TEMPORAL_MODEL/20260506_PERSON_ORGANIZATION_TEMPORAL_MODEL.md:64>) は別の概念。

Backlog や運用周期は共通 skill に固定しない。今回のローカル文書には [task-management](</Users/tatsumi.watanabe/projects/policy-cloud/main/.claude/skills/task-management/SKILL.md:14>) の「2週間・優先度ラベル」と、[運用 ADR](</Users/tatsumi.watanabe/projects/policy-cloud/main/docs/ADR/20260404_GITHUB_PROJECTS_MINIMAL_OPERATION.md:24>)・[iteration 文書](</Users/tatsumi.watanabe/projects/policy-cloud/main/docs/ITERATION_CYCLE.md:5>) の「14営業日・Backlog 手動順序」という差がある。実際の運用時に現行方針を確認する。外部への Issue 作成は依頼と既存の承認範囲に従う。
