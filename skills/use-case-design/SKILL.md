# 要求から予備設計までをつなぐ

依頼と既存の成果物を読み、今回不足する判断から始める。下の順序は目安であり、文章の添削など個別作業のために全工程を実行しない。一方、ロバストネス分析や予備設計レビューを求められた場合は、図と文章・モデルの対応確認を省いたまま完了としない。

## 必要な作業を選ぶ

| 今回足りないこと | 進めること |
| --- | --- |
| 誰の何を解き、どんな成果を得たいか | [problem-framing](../problem-framing/SKILL.md) で問題、価値、今回の範囲を整理する |
| 業務の言葉や関係を共通に説明できること | [domain-modeling](../domain-modeling/SKILL.md) で具体例から概念、関係、ルールを仮置きする |
| 誰がシステムで何を達成するか | [use-case-discovery](../use-case-discovery/SKILL.md) でアクターの目標と候補、境界を整理する |
| 実際のやり取りと結果 | [use-case-writing](../use-case-writing/SKILL.md) で基本コースと必要な代替コースを書く |
| 要求とユースケース・用語・画面の食い違い | [use-case-review](../use-case-review/SKILL.md) の要求レビューで確認する |
| 対話を成立させる対象・情報・働き | [robustness-analysis](../robustness-analysis/SKILL.md) で図を作り、本文とモデルを具体化する |
| 分析後の図・文章・モデルの整合と、詳細設計へ渡す前提 | [use-case-review](../use-case-review/SKILL.md) の予備設計レビューで確認する |

該当する skill が利用できる場合に参照する。既存の問題整理や用語集、シナリオは、現状・合意済みの定義・検討中の案を区別して引き継ぐ。スキルの試行出力や書籍の例を、対象プロジェクトのモデルや要求の根拠にしない。

## 往復して整える

ドメインモデルは暫定の共通理解として使い、完成を待ってユースケースの発見を止めない。発見・記述・分析・レビューで用語の食い違いや表せない事例が見つかったら、該当する概念・関係・ルールへ戻す。分析で必要になった属性もモデルへ返し、変更に関わるユースケースを読み直す。

対象や目的が変わったときは候補を見直す。解く価値そのものが疑わしくなった場合に problem-framing へ戻る。修正の理由と前後の状態を追えるようにし、未合意の仕様を決定済みに変えない。

## 次の作業へ渡す

目的と対象範囲、使う言葉、選んだユースケース、実施した分析・レビュー、残る判断を根拠とともに短く残す。既存の Issue・設計文書・ノートへ追記し、同じ仕様の二重管理を避ける。

受け入れ条件を使うプロジェクトでは、重要な分岐と結果を既存の受け入れ条件へ対応付ける。これは [プロジェクトへの接続](../../references/books/読書ノート/ユースケース駆動開発実践ガイド/プロジェクトへの接続.md) に記すローカル運用への適用であり、書籍のテスト設計手順とは区別する。固定の件数や新しい様式を一律に課さない。

この入口の対象は要求分析から予備設計まで。技術構成の検討は分析中から関わるため、既知の制約と未確認の前提を残す。アーキテクチャの選定、シーケンス図による詳細設計、実装、テスト設計の完了まで認定しない。境界の根拠は [第7章の補足調査](../../references/books/読書ノート/ユースケース駆動開発実践ガイド/07以降の補足調査.md) を参照する。
