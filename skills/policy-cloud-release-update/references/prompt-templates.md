# 呼び出し用プロンプトと文章の型

## 通常の更新

```text
$policy-cloud-release-update 最新に更新して。
```

既定のNotionページを対象に、今月のリリースと直近ロードマップを調査して実際に更新する。関連するモック・参考画面の挿入も含む。

## 期間・ページを変える

```text
$policy-cloud-release-update
対象ページ：{{Notion URL}}
基準日：{{YYYY/MM/DD}}
リリース対象期間：{{開始日}}〜{{終了日}}
顧客定例で使える説明と、掲載できるモックを入れて実際に更新して。
補足・訂正：{{既知のリリース状況や提供範囲。なければ省略}}
```

## 限定した更新

```text
$policy-cloud-release-update リリース予定の画像だけ見直して、Backlog・関連Issue・PRにある適切なモックを差し込んで。
```

```text
$policy-cloud-release-update リリース欄の見出しを、顧客定例のスライドにそのまま使える説明に直して。機能の提供範囲と日付は維持して。
```

## 下書きのみ

```text
$policy-cloud-release-update 今月分を調べて更新案を出して。Notionにはまだ書き込まないで。
```

## スキルを使えない環境向け

```text
PoliPoliTeam/policy-cloud-backlog を起点に policy-cloud の関連Issue・PRと公開状況を調べ、{{Notion URL}}の既存書式に従って、{{対象期間}}の顧客向けリリース案内と{{基準日}}時点の直近ロードマップを実際に更新してください。
Issueのopen/closedやPRのマージだけで公開済みと判断せず、正式・試験・一部提供を区別してください。見出しだけで「何ができ、どの手間が減るか」が伝わり、顧客定例スライドに使える日本語にしてください。社内Slack通知などの内部改善を顧客向けの新機能にしないでください。
Backlog・関連Issue・PRの画像を内容まで確認し、合う製品モックや参考画面を該当節へ挿入して、状態・変更可能性・出典を添えてください。画像がなければ準備中としてください。
現在のページを再読して差分更新し、利用者の追記や過去の節を保ってください。開発目標を公開確約にせず、保存後に文章・画像・リンクを確認してください。
```

## 本文の型

既存ページの配置・見出しレベルを優先する。この型を理由に、ユーザーが簡潔にした本文や追加画像を復元・削除しない。

### リリース欄

```markdown
## {{番号}}. ({{リリース日}}{{試験提供なら・試験提供}}) {{利用者ができるようになったこと}}。{{利用場面と減らせる手間}}。

{{製品画面。適切な画像がある場合}}

{{見出しでは説明しきれない提供範囲・条件のみ}}

[関連Backlog #{{番号}}]({{URL}})
```

見出し例：

「対象の会議体を一覧から確認」だけでは足りない。

「自社の調査対象となる会議体を、省庁・国会別の一覧から探せるようになりました。個別の会議を経由せずに詳細ページへ移動でき、議論の流れを確認しやすくなります。」

これは表現の例であり、日付・提供状況・機能範囲の根拠にはしない。

### ロードマップ欄

```markdown
# リリース予定（直近のリリースロードマップ）

{{基準日}}時点。GitHub Backlogと関連Issue・PRをもとに、開発中・準備中の機能をまとめています。{{開発目標と顧客向け公開日の区別}}

## {{番号}}. {{利用者が得られる機能を表す見出し}}

{{該当する画像}}
{{画像キャプション：開発中／試験提供、必要ならサンプルデータ・変更可能性}}

**予定・状況：** {{確認済みの開発状態・提供範囲と、目標／公開未定の区別}}

**機能：** {{何ができるか。対象データや対象利用者が限定されるなら明記}}

**背景・目的：** {{誰のどの調査・判断の手間を減らすか}}

[画面の出典]({{IssueまたはPR URL}}) ／ [関連Backlog #{{番号}}]({{URL}})
```
