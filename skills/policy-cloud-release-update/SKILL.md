# 政策クラウドのリリース案内更新

GitHubの開発情報を顧客が理解できるリリース案内に変換し、指定されたNotionページへ反映する。文章案だけで終えず、更新を依頼されたときは保存確認まで行う。下書き・調査のみの依頼では外部ページを変更しない。

## 省略時の設定

| 項目 | 既定値 |
| --- | --- |
| 対象ページ | [顧客企業向けリリース案内](https://app.notion.com/p/polipoli/2026-09-04-3d12d94ad8ea8087a7c4f44a0e2ecdbc) |
| Backlog | [PoliPoliTeam/policy-cloud-backlog](https://github.com/PoliPoliTeam/policy-cloud-backlog) |
| 実装 | [PoliPoliTeam/policy-cloud](https://github.com/PoliPoliTeam/policy-cloud) |
| 基準日 | 実行日の日本時間。過去時点の指定があれば、その時点までの情報を使う |
| リリース対象期間 | 当月初日から基準日。ページの過去月は残し、該当月の節を更新・追加する |
| ロードマップ | 既存掲載項目の現状と、Backlogで直近に提供を目指す顧客向け機能 |
| 文体・画像 | 日本語、顧客定例スライドに転記できる説明。関連する実画面・モックを差し込む |

今回の指示と現在のページを優先する。「このページだけ」「画像だけ」「タイトルだけ」などの限定があれば対象を広げない。既定値で進められる内容を毎回質問しない。期間の解釈が成果に影響する場合は、採用する期間を短く伝える。文章維持の指定があれば、画像キャプションや準備中表記も勝手に書き換えない。

## 調査とリリース判定

1. 現在のNotionページを読み、章立て・見出し階層・画像・リンク・既存の修正を把握する。過去のローカル下書きを正本にしない。
2. Backlogを起点に、本文・更新コメント・関連Issue/PR・必要なリリース／デプロイ情報を確認する。既存ロードマップの項目はopen/closedに関係なく確認し、対象期間の変更も調べる。全履歴の収集は不要。
3. 作業用に、項目ごとの「顧客ができること／公開状態／提供範囲／日付の根拠／出典／画像候補」を整理する。未確認の公開状態をマージ日から補わない。

判断では次を守る。

- **Issueのclosed、PRのmerged、顧客へのリリースを区別する。** openのままでも、リリースの証拠やユーザーの明示的な説明があればリリース済みとして扱う。closed・mergedだけでは公開済みとしない。
- ユーザーの訂正は、その機能・時点に関する直接の情報として反映する。新しい事実と矛盾する場合は根拠を照合し、不明点だけ確認する。
- 内部向けAIワークフローの一部を先行公開した場合、公開済みの機能範囲を「試験提供」として記載する。ワークフロー全体の正式公開や、独立した事業施策へ言い換えない。
- 試験提供済みの範囲はリリース欄、未提供の残りはロードマップ欄に置き、関係が分かるようにする。同じ機能全体が未提供とも公開済みとも読める重複を避ける。
- 中止が確認された項目をリリース予定として残さない。既存掲載がある場合は中止・掲載終了の扱いを現在の書式に合わせ、過去のリリース実績は保持する。Epicの未提供部分も、具体的な顧客向け計画が確認できる範囲だけを書く。
- 希望時期、古い開発目標、マイルストーンを顧客への公開確約に変えない。確認できない場合は「公開日未定」とし、古い目標を載せるなら従来の目標と明記する。
- Slack通知の書式やログなどの内部改善を、そのまま顧客向けの新機能にしない。顧客が利用できる変化を根拠付きで説明できるものを取り上げる。

## 顧客向けに書く

既存ページのフォーマットを優先し、書式・文章例は [prompt-templates.md](references/prompt-templates.md) を参照する。

- リリース見出しは、日付・提供区分に続けて「何ができるようになったか」「どの手間が減るか」を1〜2文で伝える。機能名だけの短い見出しにも、実装PRタイトルの貼り付けにもならないようにする。
- 見出しだけで顧客定例のスライドに使える内容にし、本文には提供範囲・利用場面などの補足を置く。同じ文を見出しと本文で何度も繰り返さない。
- ロードマップは、予定・状況、機能、背景・目的、画像、関連リンクを揃える。実装都合や社内用語を顧客価値に置き換え、効果の数値や未実装機能を創作しない。
- 基準日と「目標・希望時期であり、公開日は未確定」という区別を必要な箇所に示す。公開が確定した項目には確認済みの事実を書く。

## 画像を選ぶ

- Backlog本文だけでなく、関連Issue・PR・コメントの画像も確認する。リンク名で判断せず画像の内容を見る。
- 機能と現在の提供範囲に合う製品画面を選ぶ。別機能の画像、社内Notionの一覧、古い仕様の画面を製品モックとして流用しない。
- 見つかった画像はNotionの該当機能の節に表示させる。GitHubへのリンクだけで画像挿入を済ませたことにしない。
- 「開発中の画面モック」「試験提供版の参考画面」を区別し、サンプルデータや変更可能性を短いキャプションにする。出典Issue/PRへの安定したリンクを添える。
- 適切な画面がすでにページにあれば再利用できる。利用者が追加した画像を優先して確認し、不要な差し替えや重複追加を避ける。
- 画像がなければ「画面イメージ：準備中」とし、依頼なしに画像を生成しない。顧客資料に不要な個人情報・社内限定情報が映る画像は掲載候補から外す。

## Notionへ反映して確認する

利用可能なNotionコネクター/APIを優先し、未対応の操作は許可されたブラウザ操作で補う。GitHubは利用可能なコネクターまたは認証済みCLIを使う。ツール名・ログイン状態・UI座標を固定しない。ブラウザ利用時の注意点は [notion-editing.md](references/notion-editing.md) を必要時に読む。

変更前に対象箇所を再読し、現在の内容への差分を適用する。過去月、ユーザーが追記した画像・文章、対象外の節を保ち、古い全文で上書きしない。更新依頼がある場合に通常の差分編集の許可を取り直さない。共有設定変更、顧客への送信、GitHubのIssue更新はこの作業に含めない。

保存後に、公開状態・日付・見出し・画像表示・キャプション・リンク先を確認する。空の画像ブロック、重複、同じ文の繰り返しが残っていないか見る。ブラウザでは必要に応じて再読み込みで保存を確かめ、変更が分かるスクリーンショットを残す。

更新実行後の最終報告はページリンク、更新した内容、未反映の項目と理由を簡潔に伝える。下書き依頼では文章案・画像候補と出典・未確認事項を返す。アクセス不能などで書き込めない場合は完成した文章案・画像の出典を残し、反映済みとは報告しない。
