# ユースケースを記述する

関係者が読み合わせて振る舞いを確認できる、必要な対話を備えた簡潔なシナリオを書く。添削では目的と用語を保ち、判断に影響する曖昧さを具体化する。

## 入力

対象の候補、要求や顧客との会話、用語集・ドメインモデル、関係する画面・業務の具体例を確認する。
名前・目的・外部の役割と、開始に必要な状態を確かめる。アクターには外部システムも含まれる。

## 進め方と判断

- 「何が起きるか」「次に何が起きるか」をたどり、アクターとシステムの両側の行動・応答を基本コースに書く。システム側のイベントで始まる場合もあり、ユーザー操作開始を強制しない。
- ドメインモデルの用語を使い、画面を介する対話では画面名も具体的にする。利用者の操作と観測できる応答・結果、そのために必要な取得・判断・記録を具体化する。実装クラスへの責務割り当てや技術の選定までは行わない。
- 機能要求・制約は実行時の対話と分け、関連する要求として保持する。「〜できる」「〜すべき」という情報を語尾で一律に削除せず、必要な行動・応答をシナリオへ具体化して対応付ける。
- 内部アルゴリズムの詳細は別仕様、入力項目などの定義はモデルを参照し、本文には処理の名前と必要な対話を残す。既存の定義を繰り返し展開しない。
- 各ステップで「ほかに何が起こり得るか」を考える。必要な代替コースに分岐条件、システムの応答、復帰先または終了状態を書く。無関係な例外を網羅するために増やさない。
- 一つの目的に到達するまとまりを保ち、別ユースケースの内容を重複させない。原著の「2段落ルール」は短さと責任のまとまりを見直す目安として使い、機械的に分割しない。
- UIの紙芝居は操作と応答を確かめるために使い、完成品と混同させない。未決定の配置や実装方法を確定事項として埋めない。形式は依頼に必要な範囲で選び、文章だけの確認と画面・図との照合を区別する。長いテンプレートの記入を目的にしない。
- 新しく分かった概念・状態・制約はモデルや要求へ返す。未合意のルールを確定事項にせず、用語、基本・代替のつながり、終了状態を読み直す。

## 残すもの

名前・目的、基本コース、必要な代替コース、根拠となる要求へのリンクと未決事項を短く残す。
添削で意味や判断を変える場合は、元の記述 → 問題と理由 → 修正文を必要な長さで示す。続く修正でも、何が明確になり、何が未決かを追えるようにする。
既存プロジェクトへ渡す必要があれば、重要な分岐と終了状態を既存の受け入れ条件へ対応付ける。これは[プロジェクトへの接続](<../../references/books/読書ノート/ユースケース駆動開発実践ガイド/プロジェクトへの接続.md>)に記す運用判断であり、原著の必須出力や固定の件数ではない。

接続: 目的や境界が曖昧なら use-case-discovery、問題や価値が不明なら problem-framing へ。レビューを求められたら記述・関連モデル・未解決点を use-case-review に渡す。文章を図に移して不足を調べる依頼には、利用可能な [robustness-analysis](../robustness-analysis/SKILL.md) を使う。単独の記述・添削は、その依頼の範囲で完了する。
