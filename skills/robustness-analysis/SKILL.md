# ユースケースを図にして不足を見つける

選んだユースケースの基本コース・代替コース、ドメインモデル、関連画面や試作、既知の制約を使う。要求と詳細設計の間で、必要な対象と働きを明らかにする分析であり、実装クラスへのメソッド割り当てはここで決めない。

## 本文と図を往復する

1. 対象のユースケースごとに、基本コースと必要なすべての代替コースを同じ図へ表す。大きすぎて追えない場合は、代替コースを隠さず、ユースケースの分割を検討する。
2. アクターと、バウンダリ（B：画面など外部との接点）、エンティティ（E：扱う対象や情報）、コントローラ（C：システムの論理的な働き）を区別する。画面と対象は名詞、働きは動詞で名前を付ける。ボタンごとにバウンダリを増やさず、画面と操作を区別する。
3. 本文の各文を図の要素・接続へ対応付け、逆に図から本文へ戻って確認する。アクターの操作とシステムの応答、分岐条件、復帰先・終了、他ユースケースへの受け渡しを追う。図に表せない文や、図だけにある働きを見つけたら、根拠を確かめて本文も直す。
4. エンティティは既存ドメインモデルの名前を使う。入力・保持・判断・表示に必要な対象や属性が足りなければ、必要になった具体的な対話を根拠にモデルへ返す。新しい概念やルールは、現状・合意済み定義・提案を区別し、書籍例やAIの試案を承認済みの業務モデルにしない。

記法は既存の作業環境に合わせる。ASCIIなどでも要素の種類、接続、分岐を追える図にする。短文や対応表は補助に使えるが、それだけで図を作成・検証したことにはしない。

## 接続と隠れた働きを確かめる

ロバストネス図では、アクターはBとだけ接続し、名詞に当たるB・Eの間には働きを表すCを置く。

| 接続できる組み合わせ | 直接つながない組み合わせ |
| --- | --- |
| アクター―B、B―C | アクター―C、アクター―E、B―B、B―E |
| C―C、C―E | E―E |

これはロバストネス図上の通信の規則であり、ドメインモデルの概念間の関連を禁止するものではない。矢印の細部より、必要な接続と論理的な流れを明確にする。

- 画面入力からCを介してEのどの情報へ渡るか、表示にはどのEから何を取得するかを追う。ブラウザ等が処理するという実装上の都合で、本文の入力動作を図から消さない。
- 一つの画面で複数の操作を受ける場合は、BとCの間に操作名を置き、どの働きにつながるかを示す。アクターと画面の間だけに操作名を置いて曖昧にしない。
- 「表示する」の対象、エラー理由、必要な取得・初期化を確かめる。既存のCから画面への接続で表示を表せていて、固有の仕事もないなら、表示専用のCを機械的に増やさない。
- Cは一つの機能、または密接に関連する機能のまとまりとして表す。Cの数だけ実装クラスを作るとは考えない。詳細なアルゴリズム、クラスへの責務配置、設計パターンの当てはめで分析の不足を隠さない。

## 分析結果を渡す

図と改訂したユースケース、モデルの変更、残る確認事項を返す。変更が複数段階になるときは、元の状態→問題と理由→変更後をたどれるようにする。未合意の仕様は未決として明示する。

分析中から既知の技術構成や制約との食い違いを確認し、未確認の技術的な前提を詳細設計へ渡す。アーキテクチャの決定や検証まで完了したとは扱わない。分析結果の予備設計レビューが必要なら、[use-case-review](../use-case-review/SKILL.md) へつなぐ。

出典と段階的な改善例は [第5章](../../references/books/読書ノート/ユースケース駆動開発実践ガイド/05%20ロバストネス分析.md) と [第6章](../../references/books/読書ノート/ユースケース駆動開発実践ガイド/06%20予備設計レビュー.md)。技術検討の時期と今回の適用範囲は [第7章の補足調査](../../references/books/読書ノート/ユースケース駆動開発実践ガイド/07以降の補足調査.md) を参照する。
