# 設計と改善への投資判断

出荷を早める便益と、その選択によって後で増える負担を結び付けて考える。設計の美しさや「技術的負債」という呼び名だけで改善の優先度を決めず、今どこに投資する価値があるかを判断する。

依頼された意思決定の範囲に合わせて使う。通常の小さな修正にも一律に詳細な投資評価を課さず、すでに決まっている目的や実装方針を理由なく再検討しない。

## 判断の前提をそろえる

- 達成したい事業・利用者の成果、期限、対象となる変更を確認する。
- 正しさ、データ保全、合意済みの契約など、今回必ず満たす制約と、追加で選べる改善を分ける。制約を満たさない案を、出荷が早いという理由だけで推奨しない。
- 分かっている事実、見積もり、未検証の仮説を区別する。経緯・工数・売上・変更頻度などを補って事実として扱わない。

## 過去の判断と現在の投資を分ける

- 過去を評価する場合は、当時の情報と選択肢、出荷を前倒しして得た便益、その後に増えた負担を見る。今の知識だけで当時の判断を失敗と決めない。
- 早期出荷の便益は、別案より早く出せた期間に得た価値や学習などの差分として捉える。ソフトウェアが生んだ価値すべてを、設計を簡略化した効果に帰属させない。
- 過去の判断が妥当でも、今の改善が不要になるわけではない。現在の投資は、これから得られる便益と追加で必要になる費用・遅延で判断する。すでに費やした工数を回収すること自体を目的にしない。
- 当時の便益や選択肢が不明なら、過去の評価は保留し、確認できる現在の問題から今後の判断を進める。

## 現実的な選択肢を差分で比較する

現状を維持する案や最小限で出す案を比較の基準にし、必要に応じて部分改善、段階的な移行、広範な再設計を比較する。依頼に不要な選択肢を増やさない。

各案について、次の観点のうち判断に効くものを扱う。

| 観点 | 確認すること |
| --- | --- |
| 先に得られる便益 | 出荷時期、利用者の成果、収益機会、仮説検証や学習が基準案からどう変わるか |
| 今の投資 | 設計・実装・検証・移行に追加で必要な工数と、そのために遅れる仕事は何か |
| 後の負担 | どんな変更や運用で、どれだけの追加作業・不具合・調整が発生しそうか |
| 将来の事業価値 | その変更や利用はどの程度見込まれ、できるようになると誰にどんな価値があるか |
| 不確実性 | 結論が依存する前提は何か。どの前提が変わると推奨案が変わるか |

変更しにくさと将来の事業価値は別の軸として扱う。変えにくくても変更の必要性が低い部分は、改善の優先度が低いことがある。将来重要な変更を妨げている部分は、負担が顕在化する前でも投資候補になる。

比較する期間や前提をそろえ、数字がある場合は根拠と幅を示す。数字が足りない場合は定性的に比較し、計算したように見えるROIや精密な点数を作らない。追加調査は、結論を左右する不確実性を減らせるものに絞る。

## 可逆性への投資を絞る

前提が変わる見込み、変わったときの影響、戻す・移行する難しさを合わせて見る。影響の大きい不確かな前提を特定し、その部分を後で変更できるようにする最小限の備えを考える。

例えば、変動が見込まれる外部サービスとの境界だけを分離する、移行経路を確保する、小さな範囲で試す、といった案を検討する。抽象化や拡張点の追加自体にも実装・理解・保守の費用があるため、あらゆる変更に備える設計を標準解にしない。

## 判断を伝える

推奨案を先に述べ、今投資する範囲、期待する便益、受け入れる負担、判断を左右する未確認事項を簡潔に説明する。改善を先送りする場合は、変更頻度の増加や事業方針の確定など、再検討する具体的な条件を示す。

このskillは判断支援であり、実装変更の許可手順を追加しない。判断結果を依頼された作業につなげ、実行範囲はユーザーの依頼と既存の承認に従う。
